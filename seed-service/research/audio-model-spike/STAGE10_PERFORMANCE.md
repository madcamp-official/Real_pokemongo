# 10단계 성능 측정 리포트

측정 스크립트: `research/audio-model-spike/stage10-perf-measure.ts`
측정 일시: 2026-07-29, 실 CAMP-3(`root@172.10.5.71`, RTX 3090) + 실 Postgres(SSH 터널) 대상.
Fastify는 Windows 개발 머신에서 실행(참고: 이 부분은 실제 배포 환경과 다름 — "알려진 한계" 참고).

doc03 10단계의 "성능 측정" 4개 항목(10초 입력 평균/P95, 동시 요청별 지연, CPU/RAM/GPU/VRAM,
변환과 모델 추론 시간 분리)을 실측했다. doc03은 이 측정에 대해 구체적인 수치 SLA를 정의하지
않는다(완료 기준은 "테스트 통과" 계열뿐) — 그래서 이 리포트는 목표 대비 합격/불합격이 아니라
Stage 1/2 스파이크와 같은 성격의 **실측 기록**이다.

## 1. 순차 단일요청 (N=10, 10초 입력)

변환(ffmpeg)과 모델 추론을 같은 호출 안에 섞지 않고 분리해서 쟀다 — 업로드 호출은 ffmpeg
변환+품질분석까지 끝내고, identify 호출은 이미 변환된 오디오에 대해 순수 모델 왕복만 한다.

| 구간 | avg | P95 | min | max |
|---|---|---|---|---|
| 업로드(ffmpeg 변환 포함) | 503.1ms | 609.8ms | 424.8ms | 609.8ms |
| identify(모델 추론 왕복만) | 2672.8ms | 2861.3ms | 2577.1ms | 2861.3ms |

**변환은 전체 지연의 작은 부분(~500ms)이고, 모델 왕복이 지배적(~2.7초)이다.** 이 2.7초는
Stage 1 스파이크가 측정한 "재사용 세션 순수 추론 시간"(~1.0-1.1초, 3/6/10/15초 입력 전부
비슷)보다 훨씬 크다 — 즉 이 두 수치의 차이(~1.6초)는 모델 연산 자체가 아니라
**asyncio.Lock 직렬화 대기 + HTTP/JSON 오버헤드 + SSH 터널 왕복 + 세그먼트별 1024차원
임베딩 직렬화**(10초 입력 = 세그먼트 4개 × 1024 floats)에서 온다. `/internal/audio/analyze`는
Stage 6(동정)과 Stage 8(유사도)이 같은 응답에서 임베딩까지 항상 받아가도록 설계돼 있어서(각
스테이지 메모리 기록 참고), 이 페이로드 크기는 현재 설계상 불가피하다 — 만약 나중에 이
~2.7초가 제품상 체감 지연 문제로 떠오르면, 손볼 지점은 GPU가 아니라 이 직렬화/락 경합
구간이라는 게 이번 측정의 핵심 시사점이다.

## 2. 동시 요청 (8건, `Promise.all`)

| 항목 | 값 |
|---|---|
| 전체 벽시계 시간 | 9191.5ms |
| 상태코드 분포 | 200×4, 503×4 |
| 개별 identify 지연 | avg=3803.8ms, P95=9191.3ms, min=1673.1ms, max=9191.3ms |

Stage 2에서 CAMP-3에 심어둔 세마포어(cap=4)가 실제로 그대로 작동한다 — 8건 중 정확히
4건만 200, 나머지 4건은 503로 정상 거부됐다(Fastify가 이걸 `audio_processor_unavailable`로
안전하게 매핑, 죽거나 멈추지 않음, `AUDIO_MODEL_TIMEOUT_MS` 기본값 15000ms 안에서 전부
해소됨 — 관측된 최댓값 9191ms는 그 절반 정도). 개별 지연의 편차가 큰 건(min 1.7초 ~ max
9.2초) 일부 요청이 빈 슬롯을 기다리는 큐잉 시간이 그대로 응답 지연에 더해지기 때문이다 —
이 자체가 "동시 요청별 지연"에서 doc03이 알고 싶어하는 바로 그 특성이다.

## 3. CAMP-3 리소스 (GPU/VRAM/CPU, 1초 간격 샘플링, 측정 구간 전체를 포함하는 111초)

- **GPU 사용률**: 대부분 0%, 순간 최대 6%(추론이 실행되는 찰나의 펄스만 잡힘). 동시요청
  버스트 구간에서도 마찬가지.
- **VRAM**: 16523MiB로 시작부터 끝까지 완전히 고정 — 동시요청 8건을 몰아쳐도 늘지 않았다
  (누수 없음, Stage 2가 만든 `_die()`/`KillMode=control-group` 안전장치가 필요할 상황
  자체가 발생하지 않았다는 뜻이기도 하다).
- **CPU(CAMP-3)**: 0.0~0.8% 사이, 측정 시작 전 유휴 상태(baseline 확인: `nvidia-smi` GPU
  0%/16523MiB, `free -h` 사용 12Gi/49Gi, `uptime` load average 0.02)와 사실상 구분 안 될
  정도.

**결론: 이 워크로드는 RTX 3090의 연산 여력을 거의 안 쓴다.** 위 1번 항목의 ~2.7초 지연은
GPU가 바빠서가 아니다 — 오히려 GPU는 시종일관 거의 놀고 있었다. 나중에 지연을 줄이고
싶으면 더 강한 GPU가 아니라 직렬화/오버헤드 쪽을 봐야 한다는 걸 리소스 측정이 다시
확인해준다(1번의 해석과 일치).

## 4. Node(Fastify) 프로세스 메모리

동시요청 버스트 전후 RSS: 183.1MB → 164.0MB (증가 없음, 오히려 감소 — GC 타이밍 문제일 뿐
누수 신호는 아니다). CPU는 이 스크립트에서 따로 재지 않았다(아래 "알려진 한계" 참고).

## 알려진 한계 (정직하게 명시)

- **Fastify를 Windows 개발 머신에서 실행했다** — 실제 배포 환경(예: CAMP-3 자체나 별도
  서버)이 아니다. ffmpeg 변환 시간(~500ms)은 이 개발 머신의 CPU 성능에 좌우되므로, 실제
  배포 하드웨어에서는 달라질 수 있다. CAMP-3 쪽 수치(모델 추론, GPU/VRAM)는 실제 배포
  대상 그 자체이므로 그대로 신뢰할 수 있다.
- **Node 프로세스의 CPU 사용률은 재지 않았다** — RSS(메모리)만 전/후로 찍었다. 필요하면
  Windows `Get-Counter`/작업 관리자로 별도 관측해야 한다(이번 측정에선 병목이 GPU도 CPU도
  아니라 네트워크/직렬화 오버헤드로 보여 우선순위가 낮다고 판단, 스코프에서 제외).
  RTX 3090/40코어/49GB 이지만, 다른 프로젝트와 공유 중이며 디스크 72% 사용(Stage 0
  기록) — 이번 측정에는 영향 없었음을 확인했다(측정 전후 디스크/기타 프로세스 상태 불변).
- **단발 측정**(순차 10회 + 동시 8회, 각 1세트) — 통계적으로 여러 세트를 반복해 분산을
  더 좁히지는 않았다. Stage 1 스파이크가 5회 반복으로 결정론적 산출을 이미 확인했으므로,
  변동성 자체는 낮을 것으로 보이지만 이 리포트의 숫자는 "한 번 잰 값"이라는 점은 명시한다.
- **합성 chirp 오디오**(실제 새소리 아님)를 썼다 — 지연시간 특성(변환/네트워크/직렬화
  오버헤드)은 오디오 내용과 무관하지만, 모델이 실제로 무엇을 반환하는지는 이 리포트의
  관심사가 아니다(그건 Stage 1/6이 이미 실제 새소리로 검증함).
