## GPU 드라이버 복구 후 재검증 (2026-07-26, 최신 — canonical 결과)

GPU 드라이버 mismatch 해결 후, 원래 CPU 우회로 근사했던 부분(프롬프트 템플릿 80→4개
축소)을 **라이브 서비스와 완전히 동일한 조건(GPU + 공식 80개 템플릿 전체)** 으로
재계산했습니다. 아래는 이 재검증의 전체 절차와 근거이며, 이 문서의 "최종 산출물"은 이
재계산 결과 기준입니다. 구버전(CPU, 4템플릿) 산출물은 `backup_cpu4template_v1/`에
그대로 보존했습니다.

1. **사전 점검**: 새 CUDA 프로세스가 실제로 초기화되는지(`torch.cuda.is_available()`),
   venv의 torch가 CUDA 빌드인지, GPU 여유 메모리(당시 10.5GB)를 먼저 확인.
2. **소규모 타이밍 테스트**(`01a_timing_test_gpu.py`, 20종): 17.6초 → 1000종 약 15분
   추정, 피크 메모리 4.1GB — 가용 메모리 대비 안전하고 프로덕션(bioclip-inference,
   relight) 서비스에 영향 없이 처리 가능함을 실측으로 먼저 확인한 뒤 전체 실행.
3. **전체 재계산**(`01b_embed_species_gpu_full80.py`): 1000종, GPU, 공식 80템플릿 전체,
   **253.2초**에 완료. L2 정규화(`max|norm-1|=0.000001`), NaN/Inf 없음 검증 통과.
   완료 직후 `/health`(`model_loaded:true`)와 `nvidia-smi` 메모리로 프로덕션 서비스
   무영향 재확인.
4. **구/신 임베딩 정량 비교**(`02_compare_embeddings.py`): 종별 자기-유사도(구 CPU4템플릿
   vs 신 GPU80템플릿) 평균 **0.9611**(min 0.8829)로 절대적으로는 크게 다르지 않았지만,
   무작위 앵커 30종 기준 "가장 가까운 이웃 10개" 평균 겹침이 **7.87/10**(최소 6)에
   그쳐 — 로컬 근접 구조(랭킹)가 facility-location 선택 결과를 눈에 띄게 바꿀 만큼은
   흔들렸음을 확인. → CPU 근사를 canonical로 유지하지 않고 GPU 결과로 교체하기로 결정.
5. **선택 파이프라인 재실행**: `02_select_pool.py`(커버리지 곡선 재산출, 아래 표),
   `05_check_distance_distribution.py`로 거리 분포 재점검 → **고립 임계값도 절대값
   0.50을 그대로 재사용하지 않고 재보정**(아래 3절 참고), `03_worst_case_check.py`,
   `04_isolation_safety_net.py` 순으로 재실행.
6. **최종 pool 비교**: 구버전 216종 vs 신버전 213종, **공통 156종 / 구버전에만 60종 /
   신버전에만 57종**(약 72% 겹침). must-include 4종은 신버전에도 전부 포함, 중복 없음
   확인. byGroup은 대체로 안정적(fungus 33·reptile 4·amphibian 1 불변, plant
   55→53·insect 43→44·bird 30→32·mammal 6→7·other 44→39) — 극단적 재배열이 아니라
   임베딩 정확도 향상에 따른 합리적 재조정으로 판단.

### 1) 임베딩 계산 (`01_embed_species.py`, `01b_embed_species_gpu_full80.py`)

- 라이브 서비스와 동일한 모델(`hf-hub:imageomics/bioclip-2.5-vith14`, 1024차원)을 그대로 사용.
- pybioclip 공식 `CustomLabelsClassifier` 경로(OpenAI CLIP 표준 프롬프트 앙상블 +
  `encode_text`)를 그대로 재사용 — 1000종 전부를 동일한 방식으로 임베딩(일부는 사전계산된
  뱅크에서 가져오고 일부는 새로 계산하는 혼합 방식은 프롬프트 템플릿이 어긋날 위험이 있어
  피함).
- (구버전, `backup_cpu4template_v1/`) GPU 드라이버 문제로 최초엔 CPU + 축소템플릿(4개)으로
  우회했었음. **드라이버 복구 후 GPU + 공식 80템플릿 전체로 재계산해 canonical로 교체함**
  (위 재검증 절차 참고).
- 결과 검증: 전 종 L2 정규화 확인(`max|norm-1|=0.000001`) — 코사인 유사도를 내적으로 바로
  써도 되는 것 확인.

### 2) 가중 facility-location 그리디 선택 (`02_select_pool.py`)

- 거리 = 1 - 코사인유사도(내적, 임베딩이 이미 L2정규화됨).
- 가중치 w_i = 1단계의 `percentileInSource`(그룹 내부 백분위) 재사용 — 그룹 간 관측량
  스케일 차이가 이미 정규화되어 있음.
- must-include 4종(옻나무/광대버섯/유혈목이/말벌)을 항상 시드로 먼저 포함.
- 목적함수: `coverage(S) = Σ w_i * (1 - d(i, nearest(i,S)))` — submodular, 그리디 선택이
  Nemhauser et al.(1978) 기준 (1-1/e) 근사 보장.
- 여러 체크포인트(k=50~999)에서 커버리지 곡선을 함께 기록(`pool_selection_result.json`).

**커버리지 곡선(가중 평균 기준, 전형적인 diminishing-return 형태로 정상 동작 확인,
GPU+80템플릿 재계산 기준)**:

| k | coverage_ratio |
|---|---|
| 50 | 59.3% |
| 100 | 65.0% |
| 150 | 69.1% |
| 200 | 72.5% |
| 300 | 78.4% |
| 500 | 87.5% |
| 750 | 95.4% |
| 999 | 100.0% |

(구버전 CPU+4템플릿 곡선은 k=200 기준 73.4%로 거의 동일 — 임베딩 재계산이 전체적인
커버리지 성능 자체를 바꾸진 않았고, 어떤 종이 대표로 뽑히는지의 미세한 재배열만 발생함.)

### 3) 최악의 경우 점검 (`03_worst_case_check.py`, `05_check_distance_distribution.py`)

facility-location은 **평균/가중합 커버리지**를 최적화하지, "가장 안 좋게 대표되는 종
하나"까지 보장하진 않는다(min-max/k-center와는 다른 목적함수). 실측 결과 k=100~300 구간
전반에서 염소(Capra hircus)·검독수리(Aegypius monachus)·특정 나방류가 계속 거리
0.5~0.57(코사인유사도 0.43~0.5)로 남는 것을 확인 — 아무리 예산을 늘려도 이 종들에게는
"충분히 비슷한" 대표가 잘 안 생긴다는 뜻.

**처음 세운 임계값(0.45)은 성급했음** — 분포를 직접 찍어보니 k=200에서 0.45 초과가
11.5%(115종)나 됐고, 이는 "이상치"가 아니라 이 임베딩 공간의 그냥 흔한 거리(89번째
백분위 부근)였다. 재검토 후 **0.50**(같은 분포의 98번째 백분위, p99=0.507)으로 다시
잡아 16종만 남도록 조정 — 실제 "구조적으로 고립된" 종만 골라내는 값으로 보정.
(이 값은 CPU+4템플릿 임베딩 기준이며, GPU+80템플릿 재계산 후 아래처럼 다시 한 번
재보정됨.)

**GPU+80템플릿 재계산 후 임계값 2차 재보정**: 임베딩을 교체하면 절대 거리 스케일 자체가
달라지므로, 0.50을 그대로 재사용하지 않고 `05_check_distance_distribution.py`를 다시
돌려 검증했다. 실제로 새 분포에서 0.50은 k=200 기준 상위 **3.8%**(38종)를 잡아 — 구버전의
"상위 ~1%만" 기준(p99=0.507)보다 훨씬 느슨해진 상태였다(1차 재보정 때와 같은 실수를
반복할 뻔함 → 재확인해서 잡음). 새 분포의 p99(=0.5256)에 맞춰 **0.52**로 재조정하니
13종으로 정리됐고, 이 값으로 최종 pool을 확정했다.

### 4) 고립종 안전장치 (`04_isolation_safety_net.py`)

k=200 그리디 결과에서 대표까지 거리 > 0.52(위 2차 재보정값) **이면서 동시에 그룹 내
백분위 ≥ 0.3**(너무 희귀한 종은 제외)인 13종을 찾아 강제로 추가 — "촬영 대상이 될
만큼은 흔한데 임베딩 공간에서만 고립된 종"을 구제. 이건 원래 계획서의 **조건 1**("비슷한
종이 있어야 함")에 대한 데이터 기반 사후 검증이자 안전장치.

## MVP v1 (2026-07-27) — 현재 서비스에 쓰는 산출물

### 배경 — 왜 facility-location 213종을 버렸는가

213종 pool을 검토한 사용자 피드백: "비슷한 종이 최소 1개는 있어야 한다"는 조건
(facility-location의 coverage 목적함수)에 지나치게 최적화된 나머지, 균류·어류·
포유류·양서류·파충류에서 **실제로는 안 흔하거나 사람들이 잘 기록하지 않는 종**이
다수 들어갔다. 이 알고리즘은 "임베딩 공간에서 대표가 있는가"만 보지 "실제로 흔한가"는
직접 보지 않으므로, 구조적으로 이런 부작용이 생길 수 있다(README 상단 3)절의
"최악의 경우 점검"에서 이미 이 한계를 문서화했었다 — 지금 그 우려가 실제로 현실화된
사례).

또한 **도감 사진 확보·설명 작성·3D 모델링**이라는 후속 제작 비용이 종 하나하나에
실제로 드는 시점이 되면서, "커버리지"보다 "제작 가능한 범위에서 확실히 흔한 종부터"가
더 합리적인 우선순위라는 결정이 내려졌다.

### 방법론 — facility-location 완전히 배제, 순수 흔함 랭킹만 사용

- **범위 축소**: 곤충·식물·조류 3개 그룹만 이번 라운드에서 채운다. 균류·어류
  (무척추동물 포함 옛 'other' 그룹)·포유류·양서류·파충류는 **그룹 스키마(byGroup의
  키)는 유지하되 종을 0개로 비워둔다** — 스펙상 자리는 남겨서 다음 라운드에 채울 수
  있게 함. (무척추동물도 이번엔 곤충과 별개로 취급해 함께 비웠다 — 사용자 확인됨.)
- **안전 예외**: 그룹이 비는 것과 무관하게, 안전/상징 필수종 2개는 강제 유지 — 광대버섯
  (`Amanita muscaria`, 균류, "아이들에게 가장 널리 알려진 독버섯")과 유혈목이
  (`Rhabdophis tigrinus`, 파충류, "국내 서식 독사"). 아이가 실제로 마주칠 수 있는
  위험종이라 그룹 방침보다 안전이 우선한다는 사용자 판단.
- **선별 기준**: 1단계의 `percentileInSource`(그룹 내 흔함 순위, 이미 그룹 간 관측량
  스케일 차이를 정규화한 값)만으로 컷오프. facility-location(임베딩 거리 기반 coverage)은
  이번 라운드에서 아예 쓰지 않았다 — "커버리지"가 아니라 "확실히 흔한가"만 본다는 이번
  요구사항과 맞지 않기 때문.
- **컷오프 값 근거**: 아래처럼 그룹별로 percentile 구간에 따른 종수를 직접 뽑아보고
  결정했다(`build_mvp_pool.py`).

  | 컷오프 | 곤충 | 식물 | 조류 | 3그룹 합 |
  |---|---|---|---|---|
  | ≥0.9 (최상위 10%) | 30 | 31 | 18 | 79 |
  | ≥0.85 | 45 | 46 | 27 | 118 |
  | **≥0.8 (채택)** | **60** | **61** | **36** | **157** |
  | ≥0.75 | 75 | 76 | 44 | 195 |
  | ≥0.7 (상위 30%) | 90 | 91 | 53 | 234 |

  최초엔 `≥0.8`(157종)을 기본안으로 제시했으나, **사용자가 종수를 더 줄여달라고
  요청해 `≥0.9`(3그룹 79종 + 안전예외 2종 + mustInclude 보충 1종 = 82종)로 확정**했다.
  `build_mvp_pool.py`의 `PCT_THRESHOLD` 한 줄만 바꾸면 다른 컷오프로 즉시 재생성
  가능(원본 데이터 재계산 불필요, 수 초 내 완료) — 위 표의 다른 값도 그대로 시도 가능.

- **수동 제외(관측량 상위인데 "일상적으로 흔함"은 아닌 경우)**: `≥0.9` 컷오프 적용
  결과 조류 목록에 `Aegypius monachus`(독수리, bird 관측량 10위/42,354건)가 포함됐는데,
  직접 확인해보니 겨울철 철원 등 특정 급식장에 집중 관측되는 종이라 실제 "주변에서
  흔히 마주침"과는 성격이 다르다고 판단해 `MANUAL_EXCLUSIONS`로 수동 제외했다.
  제외된 자리는 다음 순위 종(`Motacilla alba`, 백할미새, 관측량 29,502건)으로 자동
  보충되도록 스크립트에 반영(목표 종수는 유지, 자리만 대체). 곤충·식물 그룹도 동일
  기준으로 전수 재확인했으나 이런 사례는 추가로 없었다.
- **그룹 내 mustInclude 강제 포함**: 컷오프 미달이어도 말벌(`Vespa mandarinia`, 곤충,
  쏘임 위험, pct=0.395라 컷오프 자체론 탈락했을 종)과 옻나무(`Toxicodendron
  vernicifluum`, 식물, 접촉성 피부염, 관측량은 최하위지만 mustInclude로 pct가 1.0으로
  강제돼 있어 자연스럽게 포함됨)는 그대로 유지.

### 국명 입력 중 추가로 발견한 오염 2건 (2026-07-27)

사용자가 82종 국명을 정리한 `82_species_table.xlsx`를 기반으로 국명을 입력하는 과정에서
**국명 중복 2쌍**을 발견했다 — 서로 다른 학명 2개가 같은 한국어 국명으로 매핑돼 있었다:

| 중복 국명 | 학명 A | 학명 B |
|---|---|---|
| 박새 | `Parus major` | `Parus cinereus` |
| 흰뺨검둥오리 | `Anas poecilorhyncha` | `Anas zonorhyncha` |

Step1의 `Pica pica` 오염 발견과 동일한 방법론으로 교차검증했다: GBIF `species/{key}/
vernacularNames`에서 **Catalogue of Life가 등록한 한국어(`kor`) 국명이 어느 쪽에
있는지** 확인한 결과, 각 쌍에서 정확히 한쪽에만 한국어 국명이 등록돼 있었다 —
`Parus cinereus`="박새"(등록됨) vs `Parus major`(미등록, 유럽/서부 고북구 중심종),
`Anas zonorhyncha`="흰뺨검둥오리"(등록됨) vs `Anas poecilorhyncha`(미등록, 남아시아
중심 Indian Spot-billed Duck). `Parus major`/`Anas poecilorhyncha`를
`build_mvp_pool.py`의 `MANUAL_EXCLUSIONS`에 추가해 제외하고, 다음 순위 조류
(`Phalacrocorax carbo`=민물가마우지, `Cyanopica cyanus`=물까치)로 자동 보충했다
(bird 최종 구성 변경, 82종 총수는 그대로 유지). 이 2종의 국명은 xlsx에 없어
`Cyanopica cyanus`는 동일 방식(GBIF/CoL)으로, `Phalacrocorax carbo`는 GBIF/CoL에도
등록이 없어 한국 조류 문헌 통용 국명("민물가마우지")을 별도 사용했다(출처를
`taxon_data_v1.json`의 `korNameSource` 필드에 명시).

### Phase 1 — 82종 Taxon 데이터 완성 (2026-07-27)

`build_taxon_data.py` → **`taxon_data_v1.json`**. `mvp_pool_v1.json`(학명·그룹·관측량만)에
`82_species_table.xlsx`의 국명을 결합하고, DB 스키마(`db/schema.sql`의 `taxon` 테이블)가
요구하는 나머지 필드를 채워 완전한 `Taxon` 형태로 만들었다.

- **taxonId**: 기존 프로덕션 7종(민들레·닭의장풀·배추흰나비·무당벌레·꿀벌·옻나무·
  광대버섯 — 개나리만 82종에서 빠져 8종 중 7종)은 `seedData.ts`의 기존 ID를 그대로
  재사용(퀘스트/DB FK 호환성 보존). 나머지 75종은 학명 기반 결정적 슬러그
  (`taxon-<genus>-<species>`)를 새로 발급 — 임의 영단어 대신 학명을 그대로 슬러그화해
  82종 규모에서도 사람 판단 없이 재현 가능하게 함.
- **국명 갱신 주의**: xlsx가 기존보다 분류학적으로 더 정확한 국명을 제시해 2종이
  바뀌었다 — 민들레→**서양민들레**(Taraxacum officinale의 정확한 국명, 토종 민들레와
  구분), 꿀벌→**양봉꿀벌 (서양종꿀벌)**(한국 토종 재래꿀벌 Apis cerana와 구분). 기존
  프로덕션 콘텐츠(있다면)에 영향 있음.
- **riskTags**: 양봉꿀벌·장수말벌→`sting_or_bite`, 광대버섯→`toxic_if_eaten`, 유혈목이→
  `sting_or_bite`(독사 물림 위험, 기존 enum 중 최근접값), 옻나무→`contact_dermatitis`
  (기존 프로덕션 태그 유지, 최초엔 4종만 지정했다가 사용자 확인 후 옻나무 추가해 5종).
- **rarity**: DB에서 `NOT NULL` 필수 필드라 반드시 채워야 함. 생태 지식을 새로
  지어내지 않고, 기존 프로덕션 선례(옻나무 count=228→uncommon, 광대버섯 count=5→
  uncommon, 나머지 6종 count≥3000대→common)와 **정확히 일치하는 규칙**
  `koreaObservationCount < 1000 → uncommon, 그 외 → common`을 그대로 적용. 결과:
  common 79종, uncommon 3종(옻나무·광대버섯·말벌).
- **seasonTags/habitatTags/aliases**: 이번 라운드에 채우지 않음(검증 안 된 생태 정보를
  지어내지 않기 위함) — 기존 7종은 `seedData.ts`의 기존 값 보존, 신규 75종은 빈 배열
  (`needsSeasonHabitatCuration: true`로 표시해 다음 작업에서 쉽게 찾을 수 있게 함).

**검증**: taxonId 82개 유일성, 국명 82개 유일성, `group`/`riskTags` 값이 DB enum
범위 내인지, rarity 전종 채워짐, 기존 7종 taxonId·seasonTags·habitatTags 회귀 없음,
riskTags가 정확히 지정된 4종에만 적용됐는지 — 전부 스크립트 내 assert로 확인 후
82/82·common 79/uncommon 3 결과 재확인.

### Phase 2 — 백엔드/GPU 모델 실제 반영 (2026-07-27)

`taxon_data_v1.json`(82종)을 실제 서비스에 배선했다. 핵심 발견: `seed-service`엔
별도 DB 시드 스크립트가 없고, `composition.ts`가 **부팅할 때마다**
`repos.taxa.upsertMany(SEED_TAXA)`를 호출한다(InMemory/Postgres 두 모드 공통) —
즉 `seedData.ts`만 고치고 서버를 재시작하면 실DB에도 자동 반영된다.

- **`seedData.ts`의 `SEED_TAXA`를 8종→82종으로 교체**. taxonId는 기존 프로덕션 7종
  (개나리만 82종에서 빠짐)은 기존 ID 유지, 신규 75종은 학명 슬러그로 신규 발급.
- **BioClipProvider.supports**에 `bird`/`reptile` 추가, `domain/types.ts`의
  stale해진 "새/양서류는 MVP 제외" 주석도 현재 상태에 맞게 갱신 — 코드가 실제로
  하는 일과 주석이 다시 일치하도록 함.
- **실 프로덕션 DB 점검**: 82종에 반영하기 전 Postgres를 직접 조회해, 개나리

### Phase 3 — 오동정 방지(조건 2, 혼동 종 분석) (2026-07-27)

원래 알고리즘 설계(세션 최초 분석)의 조건 2 — "비슷한 종끼리 서로 오분류되면 안 된다"
— 를 다뤘다. GPU 서버의 open-set 교차검증(`bioclip_hybrid.py`)은 "82종 후보 밖의
세상과 비교해 말이 되는가"만 검증하고, "82종 안에서 서로 닮은 둘 중 어느 쪽인가"는
검증하지 않는다는 걸 코드 추적으로 확인 — 서로 다른 실패 모드라 이번 작업이
그 위의 별개 방어선이 된다.

- **분석**(`03_confusion_analysis.py`): 82종의 GPU+80템플릿 텍스트 임베딩(이미 계산돼
  있어 재계산 불필요, `embeddings.npy`에서 슬라이스)으로 82×82 코사인 유사도 계산.
  CLIP류 모델은 텍스트-이미지 zero-shot 매칭이 핵심이라 텍스트 임베딩 유사도가 실제
  사진 분류 시 혼동 가능성의 합리적 프록시가 된다(완벽하진 않음 — 아래 한계 참고).
- **임계값 근거**: 최근접 이웃 유사도 분포(median=0.56, p75=0.63, p90=0.70, p95=0.75)를
  직접 찍어보고 **0.60**으로 결정(median보다 뚜렷이 높으면서 상위 쌍을 놓치지 않는
  지점) — 지금까지 이 프로젝트에서 반복해온 "분포 확인 없이 임계값 정하지 않기"
  원칙 그대로 적용.
- **결과**: 16개 혼동 쌍 발견, 상위권이 전부 생물학적으로 말이 되는 쌍 — 같은 속
  (두점하루살이/네점하루살이, 개망초/망초, 신갈나무/굴참나무, 왜가리/대백로,
  배추흰나비/큰배추흰나비, 청둥오리/흰뺨검둥오리) 또는 형태적으로 실제로 닮은
  다른 속 쌍(무당벌레/칠성무당벌레, 호리꽃등에/꼬마꽃등에 등). 청둥오리/흰뺨검둥오리
  쌍은 Phase 1에서 국명 중복으로 잡아낸 오염 검증(Anas 속) 결과와도 정합적이다.
- **구현**(`confusionPairs.ts` + `IdentificationGateway.identify()`): 혼동 쌍 16개를
  코드에 상수로 내장(`isConfusablePair()` 순수함수). 게이트웨이가 tier를 high로
  판정해도, **top1/top2가 알려진 혼동 쌍이면서 확신도 차이가 0.05 미만**일 때만
  medium으로 강등해 아이가 직접 고르게 한다 — 무조건 강등이 아니라 "진짜 애매할
  때만" 개입(margin이 충분히 크면 혼동 쌍이어도 그대로 단정).
- **검증**: 유닛테스트 7건 추가(순수함수 4건 + 게이트웨이 통합 3건 — 강등/유지/오탐
  방지 시나리오) 전부 통과, 전체 스위트 205/205, typecheck 0에러, 실행 중인
  seed-service 재기동 후 정상 기동 확인.

**알려진 한계**: 텍스트 임베딩 유사도는 "같은 속/비슷한 생김새"뿐 아니라 "같은
문구로 자주 묘사되는 종"에도 반응해 완벽한 시각적 유사도 프록시는 아니다(예:
네발나비 vs 남방노랑나비는 실제로는 꽤 다르게 생겼는데도 목록에 포함됨). 다만
이 목록에 있다고 무조건 강등되는 게 아니라 margin이 실제로 작을 때만 개입하므로,
오탐의 비용은 "가끔 불필요하게 되물어보는 것" 정도로 작다 — "틀릴 땐 안전하게
틀린다" 원칙과 맞아 보수적으로 넉넉히 잡아뒀다. `CONFUSION_MARGIN_THRESHOLD`(0.05)는
실측 데이터 없는 최초값이라 확신도 분포 실측 후 튜닝 대상(`confidencePolicy.ts`의
`DEFAULT_THRESHOLDS`와 같은 성격).

### INCONCLUSIVE 3종 해결 (2026-07-27)

위에서 잔존 위험으로 남겨뒀던 흰부채하루살이/줄날도래/네점하루살이 문제를 실제로
해결했다.

**원인 확정**: GPU 서버의 오픈셋 텍스트 뱅크(`TreeOfLife-200M`, 794,878종)를 직접
JSON 캐시 파일에서 검색해봤다 — 이 3종의 학명이 정확히 없다(속 자체는 있음:
`Epeorus` 16종, `Cheumatopsyche` 70종, `Ecdyonurus` 28종이 있는데 우리 3종만
빠짐). 오픈셋은 고정된 외부 사전학습 데이터셋이라 우리가 채워 넣을 수 없다 —
남은 유일한 수단은 `bioclip_hybrid.py`의 두 번째 검증 경로인 프로토타입 뱅크
(실제 참조사진의 이미지 임베딩 평균)뿐이었다.

**해결**: GBIF occurrence multimedia에서 이 3종의 라이선스 확인된(CC-BY-NC/
CC-BY-NC-SA, 무료) 실제 사진을 찾아 프로토타입을 만들었다.

1. 참조사진 수급(GPU 서버에서 직접 다운로드): 흰부채하루살이 5장(iNaturalist),
   줄날도래 2장(BOLD Systems), 네점하루살이 1장(iNaturalist) — GBIF에 실제로
   있는 전부.
2. 전부 `PIL.Image.verify()`로 무결성 확인 통과.
3. 라이브 서비스와 완전히 동일한 모델(`hf-hub:imageomics/bioclip-2.5-vith14`)의
   이미지 인코더로 임베딩 계산 — 종별로 사진이 2장 이상이면 1장을 검증용으로
   따로 빼두고 나머지로 프로토타입(평균 후 재정규화)을 만듦(네점하루살이는
   1장뿐이라 held-out 없이 그 1장을 그대로 프로토타입으로 사용 — 문서화된 한계).
4. **held-out 교차검증**(프로토타입 계산에 안 쓴 별도 사진으로): 흰부채하루살이
   own_sim=0.655, 줄날도래 own_sim=0.921 — 전부 자기 자신이 최근접이면서
   기존 `MIN_PROTOTYPE_SIMILARITY`(0.4, 유혈목이 실측 기반) 임계값을 여유 있게
   상회. 기존 유혈목이 재계산 결과도 own_sim=0.4793로 원래 기록과 정확히 일치

5. `prototype_bank.json`을 1종→4종으로 갱신(기존 유혈목이 그대로 보존), 배포

6. `bioclip-inference.service` 재시작 → 기동 로그에서 `[HybridClassifier] 경고`

7. **실제 held-out 이미지로 라이브 `/identify` 호출**: `verdict=AGREE
   final_tier=high method=prototype` — 이전엔 이 3종에 대해 `method=none`으로

   79종과 동등하게 실제 교차검증을 받는다.
8. 프로덕션 서비스(`bioclip-inference`/`relight`/`render`/`nginx`/`postgresql`/

**흥미로운 부수 확인**: held-out 검증 중 흰부채하루살이 사진이 네점하루살이
프로토타입과도 유사도 0.583으로 꽤 높게 나왔다 — 실제 이미지 임베딩 기준으로도
이 둘이 시각적으로 닮았다는 뜻이다. Phase 3의 텍스트 임베딩 기반 혼동 쌍 분석에서
이 두 종이 실제로 혼동 쌍으로 잡혔던 것과 정확히 정합적 — 서로 다른 두 방법(텍스트
